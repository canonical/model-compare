How to use

Plug the live rankings into OpenCode, steer OpenRouter requests to the exact endpoint we priced, or pull the published JSON feeds into your own tools.

OpenCode v1 — Launch flag, shell alias

OpenCode v1 lets you pass a model ID straight on the command line with --model. Alongside the web tables, this site publishes a tiny plain-text file — best.txt — that always holds the current balanced #1 pick, refreshed every 3 hours.

Drop this alias into your shell config (.bashrc, .zshrc, and similar), and every launch will pick up the freshest winner automatically: 

alias oc-best='opencode --model "$(curl -fsSL https://model-compare.dev/best.txt)"'

Nothing fancy, but you never have to check the table or copy-paste a model ID by hand.

OpenCode v2 — model-compare plugin

OpenCode v2 dropped the --model flag for interactive TUI sessions. Instead, install model-compare-opencode-plugin: it adds live balanced, price, and quality aliases right into your OpenRouter model picker, keeps them updated while you work, steers requests to the ranked endpoint, and pins reasoning depth.

See the OpenCode plugin tab for setup, examples, and keyboard shortcuts.

How do I pin routing with the steering block?

When you call OpenRouter with just a model name, OpenRouter decides which backend provider handles your request. As explained in the FAQ, that default route can land on a pricier provider — or on a more heavily compressed quantization — than the one that earned the model its spot on the Picks page.

To get the exact setup we ranked, attach OpenRouter's provider routing object to your request. You don't have to put it together yourself: every ranked model in the published catalog.json file includes a ready-made steering block: 

{
    "model": "deepseek/deepseek-v4.1-flash-1017",
    "provider": {
      "order": ["DeepInfra/fp8", "Baidu/bf16"],
      "ignore": ["Morph/int4"],
      "quantizations": ["bf16", "fp8"],
      "allow_fallbacks": true
    }
  }

Here is what each piece inside provider does:

  • order — eligible backend providers, listed cheapest first, so OpenRouter tries the best-value option first.
  • ignore — live providers excluded from the ranking (for instance, lower-precision quantizations or incompatible pricing tiers).
  • quantizations — acceptable precision levels, at or above the model's baseline (left out when providers don't disclose precision).
  • allow_fallbacks — lets OpenRouter fall back if every provider listed in order is temporarily unavailable, rather than failing the request (while still honoring ignore and quantizations).

Pass that provider object along with your API request as is. If you're using Python's OpenAI SDK, put it inside extra_body — the SDK strips unfamiliar top-level arguments before sending the call: 

client.chat.completions.create(
    model="deepseek/deepseek-v4.1-flash-1017",
    messages=[…],
    extra_body={"provider": steering["provider"]},
  )

Using OpenCode v2? The OpenCode plugin injects this block for you automatically whenever you use one of its aliases.

How do I verify which endpoint served a call?

Every completion response from OpenRouter includes a provider field naming the backend that actually answered. Check it against the row's expanded Providers table on the Picks page (where ✓ marks the ranked endpoint) — or against steering.provider.order[0] if you pinned routing.

For billing ground truth, open the Activity view in your OpenRouter dashboard. It logs the serving provider, exact price, and latency for each request. (In OpenCode with the plugin installed, you can also press alt+e to pop up a quick toast showing which endpoint served your last reply.)

How do I pull the live rankings into my own scripts?

Everything powering this site is published as static files over HTTPS and rebuilt every 3 hours. You don't need an API key, and you don't need to scrape HTML:

  • best.txt — just the current balanced #1 model ID on a single line (openrouter/<provider>/<model>), ideal for shell one-liners.
  • data.json — the top 20 rows for balanced, price, and quality, plus the off-peak deals list and the refresh timestamp.
  • catalog.json — the full dataset: every ranked candidate (and every filtered-out model, with the reason it was dropped), per-endpoint pricing, reasoning-depth scores, and steering blocks.

For example, to grab the current #1 quality pick with curl and jq: 

curl -fsSL https://model-compare.dev/data.json | jq -r '.priorities.quality[0].opencode_model'

How do I use these prices and routing rules with LiteLLM?

If you route traffic through a LiteLLM proxy, its built-in cost map only knows OpenRouter's headline rates — not per-endpoint prices, long-context tiers, or off-peak discount windows.

On every refresh, this site publishes litellm.json: LiteLLM's upstream price map merged with accurate openrouter/<model> entries for every ranked candidate. Point LiteLLM at it in your environment before starting the proxy: 

export LITELLM_MODEL_COST_MAP_URL=https://model-compare.dev/litellm.json

Two companion files are published alongside it if you want finer control: litellm_rate_card.json (just our openrouter/ entries, if you prefer merging upstream yourself) and litellm_steering.json (matching provider routing profiles and scored reasoning depths, ready for a LiteLLM pre-call hook). See the LiteLLM section in DESIGN.md for hook wiring and edge cases.
