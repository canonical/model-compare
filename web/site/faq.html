What do PREC and the "!" marker mean?

On OpenRouter, a single model name isn't necessarily tied to one company's servers. Several backend providers ("endpoints") can host the exact same open-weight model at different prices and compression levels.

That compression is called quantization: converting a model's high-precision weights (such as bf16) into smaller number formats (such as fp8 or int4). It cuts memory use and speeds up replies — though pushing it too far can chip away at answer quality.

Rather than taking OpenRouter's headline number at face value, model-compare checks every live endpoint for a model and ranks it using the cheapest eligible one that meets (or beats) the model's baseline precision. The PREC column shows that baseline precision — the model maker's disclosed format, the best format disclosed across live providers, or n/a when none is disclosed.

A trailing ! (for example, fp8!) is a heads-up. Left to its own devices, OpenRouter weights traffic toward whichever provider is cheapest overall — and the ! means even cheaper, lower-precision endpoints exist and would soak up more than half of your requests by default.

The upshot: without routing rules, your calls can quietly land on a more heavily compressed version of the model than the row describes. Hover the PREC cell (or click the row) to inspect the competing endpoints, their precisions, and their prices — and see How to use for how to lock routing down.

Why can the price I pay differ from the ranked price?

If you compare a row here against the model's page on openrouter.ai, the two prices often won't match. That's by design: OpenRouter's page shows the rate for its default route, while this site quotes the cheapest eligible endpoint.

To judge overall value for money, model-compare blends input and output prices at a 75% / 25% split. Coding sessions tend to send plenty of file context in and get comparatively short patches back, so weighting input heavier reflects real usage much better than a 50 / 50 average.

In practice, three things can nudge your actual bill away from the table price:

  • Default routing: if you don't pin your provider list, OpenRouter may route a call to a pricier (or cheaper) backend than the one ranked here.
  • Long-context tiers (TIER shows >200k, >272k, and similar): some providers charge more per token once a conversation grows past a prompt-size threshold. To avoid bait-and-switch starter rates, model-compare always evaluates prices at a 1M-token prompt size — what a long coding session actually pays.
  • Off-peak discounts (TIER shows -38%, and similar): a few providers cut rates during quieter UTC hours. The main table sticks to standard rates so the ranking stays predictable, while the Off-peak deals table highlights those scheduled windows separately.

What about reasoning depths and model variants?

Many newer "thinking" models let you dial in how much effort they spend reasoning before they answer — levels like minimal, low, medium, high, or max. More thinking generally lifts answer quality, at the cost of extra internal tokens and a higher bill per task.

Quality scores (QUAL) come from the Artificial Analysis intelligence index, which often benchmarks the same model across several thinking levels. Each row here is scored at the model's highest-rated depth that OpenRouter actually lets you select, and DEPTH tells you which one won (an asterisk like max* just notes that it also happens to be OpenRouter's default).

Click any row on the Picks page to unfold its full depth table — quality score, benchmark cost, and a button to copy the ready-to-use ID. In OpenCode, you pick a depth by tacking #<depth> onto the model ID, such as openrouter/deepseek/deepseek-v4.1-flash-1017#max (or #xhigh, #high, #medium, #low, #minimal, or #none). If you use the OpenCode plugin, it pins that scored depth automatically.

One more wrinkle: suffixes like :free (rate-limited free tier) and :batch (asynchronous batch jobs) are separate listings on OpenRouter with their own limits, context windows, and pricing. The rankings skip :batch listings because interactive coding tools need live replies, and include :free listings when they pass every other check. Treat them as distinct models — don't pair a variant ID with another row's routing block.

Why are some popular models missing from the main table?

The main ranking applies a few strict filters up front so every pick is practical (and safe) for day-to-day coding work:

  • Zero-data-retention (ZDR) only: a model must have at least one live ZDR endpoint — a provider committed to not storing or training on your prompts and completions. An endpoint that only offers Safety Retention does not count: it may keep prompts and responses to investigate abuse. Google's models are the exception here, because that is what our guardrail allows.
  • 1M-token context window: models with smaller context limits are filtered out so long agent sessions don't hit a wall mid-task.
  • Tool calling: models that can't call functions or tools aren't usable in coding agents and are excluded.

Need something looser for your own workflow? Every one of those filters is configurable when you run model_compare.py on the command line — you can lower the context-window floor, include non-ZDR providers, or drop the tool-calling check. See the repository README for the options.

And if you spot a model in Off-peak deals that doesn't appear in the main ranking above it, that's expected: the deals table is a straight index of scheduled discounts across OpenRouter and deliberately skips the ZDR and context-window filters.
