model-compare FAQ

Precision, price and routing, explained for the numbers on the picks page. The column definitions live in the table's header tooltips; this page covers what to do when the numbers differ from your bill.

What do PREC and the "!" marker mean?

PREC is the quantization the ranked endpoint quotes (fp8, bf16, int4, …), not a property of the model. One model id can be served by several endpoints at different precisions and prices.

The tool ranks at the cheapest eligible endpoint, so PREC names that endpoint's precision. A trailing ! is a warning: OpenRouter's default routing weights endpoints by price, and cheaper endpoints below the quoted precision would take more than half the traffic. In other words, without steering, a call may land on a lower-precision endpoint than the row claims. Hover the cell for the cheapest non-baseline endpoint (quantization, provider and price).

Why can the price I pay differ from the ranked price?

Prices here are the cheapest eligible endpoint's, blended 75% input / 25% output (the --input-share default). openrouter.ai shows the default endpoint's listed rate. Neither is wrong: one answers "what is the best value available", the other "what does the default route cost".

Three things move the actual bill: default routing sending traffic to a different endpoint, long prompts crossing a tier threshold into a pricier rate (TIER shows >Nk), and scheduled off-peak windows (TIER shows -N%). The ranked price is deterministic at --min-context, which is why it makes a fair comparison across models.

How do I pin routing with the steering block?

Every --json row and every catalog.json model entry carries a steering object: the exact OpenRouter provider routing block that reproduces the ranked choice. 

{
  "model": "deepseek/deepseek-v4.1-flash-1017",
  "provider": {
    "order": ["DeepInfra/fp8", "Baidu/bf16"],
    "ignore": ["Morph/int4"],
    "quantizations": ["bf16", "fp8"],
    "allow_fallbacks": true
  }
}

order lists baseline-eligible endpoints, cheapest first; ignore names every live endpoint that is not eligible (lower-precision, unknown, or price-tier gated); quantizations keeps only precisions at or above the quoted one (the key is omitted when the default precision is unknown); allow_fallbacks lets OpenRouter fall back when the ordered endpoints are unavailable. Pass the provider object with your request, as-is.

With the OpenAI SDK, add it through extra_body — unknown top-level parameters are dropped before the request is sent: 

client.chat.completions.create(
  model="deepseek/deepseek-v4.1-flash-1017",
  messages=[…],
  extra_body={"provider": steering["provider"]},
)

In OpenCode, the model-compare plugin applies the same block for you; a custom request body can be supplied with its body option, which is forwarded to the provider request — put the provider object there.

How do I verify which endpoint served a call?

The completion response carries the serving endpoint's provider field; compare it with the row's PREC and, for the ranked choice, with steering.order[0]. The OpenRouter dashboard's activity view shows per-request provider, price and latency, which is the ground truth for what you were billed.

What about depths and variants?

Reasoning depth is part of the model id in OpenCode: append #max, #high, #medium, #low, #minimal or #none to pin the effort (for example openrouter/deepseek/deepseek-v4.1-flash-1017#max). The ranked QUAL is measured at the model's best measured selectable depth, and the depth detail row shows each effort's index, cost and the suffix that selects it. A pinned depth can cost more than the default one.

:free and :batch ids are separate listings with their own prices, context and eligibility; the ranked picks exclude :batch by default and exclude :free only with --exclude-free, and the steering.ignore list already names the live variants that were not eligible. Do not mix a variant id with another row's steering block.
